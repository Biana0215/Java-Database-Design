# 医院挂号系统 · 四人分工表

> 原则：每人一块**能独立演示**的业务 + 一项职能。答辩按人提问，这是“组内参与情况”的评分依据。

## 一、分工

| 成员 | 职能主责 | 业务模块（功能编号） | 具体交付物 | 答辩主打 |
|---|---|---|---|---|
| **A** | 数据库设计与 SQL | 排班与号源（F05 / F06 / F07） | `sql/01_schema.sql`、`02_data.sql`、复杂查询清单、索引与视图、数据库设计说明书 | 表结构、范式、索引为什么这么建 |
| **B** | 后端业务与事务 | 挂号 / 退号 / 收费（F08–F14） | DAO 与 Service 层、事务与并发处理、该模块测试用例 | 重复挂号怎么防、退号事务怎么做 |
| **C** | 界面框架与报表 | 医生工作台 + 统计（F15–F20） | 主窗体与登录、通用表格/表单组件、四张统计报表 | 功能演示主线 |
| **D** | 需求与文档统稿 | 患者 / 科室 / 医生 / 系统（F01–F04、F21、F22） | 用例图、DFD、数据字典、报告统稿、答辩 PPT | 需求怎么来的、模块怎么划分的 |

> 界面不是 C 一个人的事：A、B、D 各自完成**自己模块**的界面，C 只负责公共框架（主窗体、登录、表格封装），否则 C 会变成瓶颈。

## 二、协作约定（第一天就定下来）

- **分支**：`main` 只放可运行版本，各人开 `feat/A-schedule`、`feat/B-reg` 这类分支，每天下班前合并一次。
- **提交信息**：`[A] 完成排班生成 F05`，方便最后导出提交记录当分工证据。
- **接口先约定**：动代码前先把 DAO 方法签名定下来写进 `docs/04_接口约定.md`，例如
  `SlotDao.findAvailable(int scheduleId)`、`RegistrationService.register(int patientId, int slotId, int operatorId)`。
  四个人的代码靠这个对齐，比口头说管用。
- **数据库唯一入口**：任何建表、改表都走 A 手里的 `01_schema.sql`，别人不直接改库结构。
- **造数**：A 提供 `02_data.sql`（科室 10 / 医生 40 / 患者 300 / 挂号单 1000），B、C、D 都从这份数据开发，保证联调时数据一致。

## 四、答辩预演问题（每人准备自己那份）

1. 为什么号源要单独一张表，不在排班表里存剩余数？
2. 两个人同时挂同一个号会怎样？你的代码怎么保证不重复？
3. 退号涉及哪几张表的修改？为什么必须用事务？
4. `registration.reg_fee` 和 `doctor.reg_fee` 重复了，算违反 3NF 吗？
5. 你的模块用了哪几条复杂查询？走没走索引？
6. 这部分代码是谁写的？讲讲实现思路。
